The <Term id="api-key">API key</Term> is in a commit. You delete the line in a second commit. The first commit is still in <Term id="git">git</Term> history. Anyone who can read the repository can read the key. Scanning matters before the push, and rotation matters after a miss.

</Hook>

## The idea

GitHub's push protection is a secret-scanning feature that blocks a push when it detects a secret, so the secret does not reach the repository. The docs say it can block pushes from the command line, commits made in the GitHub UI, file uploads, REST API requests, and, on public repositories, interactions with the GitHub MCP server. Push protection for your own GitHub.com user is on by default and stops you from pushing secrets to public repositories. Repository push protection is separate: the docs say it requires GitHub Secret Protection, is off until an admin turns it on, and then blocks pushes to that repository.

Turn the repository setting on if your plan includes it. Do not skip a local check because you hope the server will catch it. A private repo without the setting will accept the push. A local pre-commit command can fail when `git ls-files` lists `.env`, or when a diff introduces a token prefix you care about, such as `sk_live`.

The docs also say that, by default, someone with write access can bypass repository push protection by giving a reason. A bypass is an incident to look at, not a button for a deadline. This page does not walk through bypassing it. If a push is blocked, remove the secret and try again.

If the secret already landed, rotate it at the vendor. Rewriting history on a branch nobody else has is a person decision, and it does not un-leak a key that was pushed to a remote. Assume it was copied. Part 8's rule stands: the value lives in the environment, not in the tree.

## Real example

Two commands before you push:

```
git ls-files .env
git diff -U0 | findstr sk_live
```

On a shell without `findstr`, search the diff for that prefix another way. Empty output is what you want. A hit means you stop and rotate if the value is real. `findstr` is Windows. The test is the same everywhere: the secret is not in the patch.

<TryIt minutes={5}>

Run `git ls-files .env` in a repo you care about. Write "tracked" or "not tracked." If it is tracked, rotate the key and remove the file from the index before any new feature work.

</TryIt>

<Mistake>

Deleting the line and calling the key safe. The old commit still has it. Rotate first. Then clean the tree. A new commit that omits the key does not erase the old one.

</Mistake>
